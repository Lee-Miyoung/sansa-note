**초안이며 검증 완료본이 아니다. 운영 Firebase 규칙을 변경하지 않았고 PR을 병합하지 않았다.**

사용자가 직접 확인해 제공한 현행 규칙을 입력으로 사용했다. 서버에서 현행 규칙을 다시 조회해 대조한 것은 아니다.

## 권한 상속과 실제 효과

Firebase Realtime Database는 상위 경로에서 허용한 `.read`/`.write`를 하위 규칙으로 취소할 수 없다.

- 본인은 기존 `users/$uid/.write`에 의해 자신의 비밀도감에도 쓸 수 있다. 하위 `.write`를 더 엄격하게 써도 이 상위 허용을 철회할 수 없다.
- 다른 일반 사용자는 타인의 비밀도감을 읽거나 쓸 권한이 없다.
- 지정된 관리자는 기존 `users/.read`와 사용자 경로의 읽기 예외에 의해 다른 사용자의 비밀도감도 읽을 수 있다. 이 예외를 유지했다. ‘모든 다른 계정의 읽기가 차단된다’고 설명하지 않는다.
- 관리자의 타인 경로 쓰기 권한은 추가하지 않았다. 관리자라도 자신의 UID가 아닌 사용자의 경로에는 제공된 규칙상 쓰기 권한이 없다.
- `.validate`는 권한을 부여하거나 취소하는 규칙이 아니다. 쓰기가 허용된 요청에 대해 삭제되지 않고 남는 데이터가 형태·범위·참조 조건을 만족하는지 검사한다. 상위 쓰기 허용이 있어도 이 데이터 검증은 통과해야 한다.

위 설명은 규칙의 의미를 검토한 결과이며 이 환경에서 실제 Firebase 엔진으로 통과시킨 결과는 아니다.

## 해인사 데이터 검증

새 검증은 `users/$uid/secretAtlas/haeinsa-001`에만 적용한다.

- 장면 번호 0~11, 완료 장면 키 1~12, 문제 키 q1~q6, 카드 키 001~003.
- 시각은 숫자 범위, 문제 답은 0~5 정수의 연속 인덱스 목록, 정오답은 boolean, 시도 횟수는 정수.
- 감상은 최대 10,000자 문자열과 수정 시각. 감상을 비울 때는 `text: ''`를 저장하며 전체 노드 삭제와 구분한다.
- 각 카드의 해당 네 장면 완료 조건 및 최초 획득 시각 불변.
- 해인사 노드 자체에도 카드/완료 장면 간 관계를 검사하는 `.validate`를 두었다. 따라서 해인사 노드를 남긴 채 카드만 삭제하거나, 획득 카드의 필수 완료 장면만 삭제하는 요청도 거부하도록 작성했다.
- 현장 인증 참조는 같은 사용자의 기존 `destinations/{templeId}`에서 사찰명이 해인사이며 해당 `visits/{visitId}/verified`가 true인지 검사한다.
- 기존 방문 기록은 본인 쓰기가 가능한 기존 체계다. 새 규칙은 GPS를 서버에서 재측정하거나 기존 verified 값의 진위를 별도로 보증하는 인증 서버가 아니다. 기존 방문 인증의 신뢰 모델을 유지한다.
- 해인사의 미지정 필드는 거부한다. 새 기능 스키마만 검사하며 기존 일기·사진·방문·108 관련 필드를 덮어쓰지 않는다.

## 삭제 한계 — 전체 삭제 금지는 보장하지 않음

`.validate`는 해당 노드가 삭제되어 새 값이 null일 때 실행되지 않는다.

| 요청 | 규칙 의미상 예상 결과 |
|---|---|
| 다른 일반 사용자가 A의 에피소드 삭제 | 기존 쓰기 권한에 의해 거부 |
| A가 에피소드를 유지하며 획득 카드만 삭제 | 에피소드 부모의 카드 유지 조건에 의해 거부하도록 작성 |
| A가 획득 카드의 필수 완료 장면만 삭제 | 에피소드 부모의 완료 조건에 의해 거부하도록 작성 |
| A가 특정 답안 또는 선택적 인증 참조 전체를 삭제 | 해당 노드의 검증은 건너뛰며 부모 조건에 위배되지 않으면 허용 |
| A가 `haeinsa-001` 전체를 삭제 | 상위 본인 쓰기 허용이 있고 해당 검증 노드도 삭제되므로 허용 |
| A가 자신의 `secretAtlas` 또는 사용자 노드 전체를 삭제 | 기존 상위 쓰기 권한 구조상 허용될 수 있음 |

부모가 남는 부분 삭제에 대한 검증과, 검증 부모까지 없애는 전체 삭제를 구분해야 한다. 이번 초안은 기존 상위 권한을 그대로 보존하므로 **사용자 본인의 에피소드 전체 삭제를 금지할 수 없다.** 이를 완전히 금지하려면 상위 쓰기 정책이나 신뢰할 수 있는 서버 쓰기 구조를 별도로 설계해야 하며, 이번 작업에서는 그런 변경을 하지 않았다. 앱도 삭제/초기화 동작을 새로 추가하지 않았다.

## 향후 에피소드 확장

기존 조각의 `secretAtlas/$other: { ".validate": false }`는 새 불국사 등의 노드도 거부하므로 제거했다.

- 해인사 내부의 미지정 필드 거부는 유지한다.
- 다른 에피소드 경로는 기존 본인 읽기·쓰기 권한을 상속한다.
- **다른 에피소드에는 아직 전용 스키마 검증이 없다.** 확장을 막지 않는 것과 미래 콘텐츠의 데이터가 검증되는 것은 다르다. 새 에피소드를 출시하기 전에 그 에피소드의 검증 노드를 추가해야 한다.
- 다른 에피소드 기능이나 콘텐츠를 새로 구현한 것은 아니다.

`tests/secret-atlas-rules.cjs`는 이제 **제공된 운영 규칙과 병합한 전체 JSON만** 불러온다. 조각 단독 검사를 전체 규칙 검증으로 취급하지 않는다. 준비한 실행 사례:

1. A와 B 각각 진행 위치·감상 저장/조회 및 양방향 타인 읽기·쓰기 거부.
2. 관리자 읽기 예외 유지 및 타인 쓰기 거부, 미인증 접근 거부.
3. 카드 최초 획득·중복 transaction·획득 시각 변경 거부.
4. 새 세션 컨텍스트에서 진행·감상 재조회. 에뮬레이터 인증 컨텍스트이므로 실제 Google 재로그인 검사와 구분한다.
5. 기존 방문·사진·108의 원천 기록 fixture가 그대로인지 비교.
6. 잘못된 타입·범위·미지정 필드·가짜 인증 참조 거부.
7. 카드 부분 삭제 거부와 에피소드 전체 삭제 허용을 서로 구분하여 확인.
8. 미래 테스트 에피소드의 본인 접근 허용과 타인 접근 거부.
9. 기존 shared/커뮤니티/게임 점수의 접근 정책 보존.

이 사례들은 엔진 실행 전까지 **예상 결과를 명시한 준비된 테스트**다. 통과했다고 주장하지 않는다.

## 실제 계정 검증을 재개할 조건

익명 인증이나 신규 회원가입 설정은 바꾸지 않는다. 사용자가 기존 로그인 방식으로 사용할 수 있는 별도 테스트 계정 두 개를 준비했을 때, 사용자가 직접 로그인하는 검증 환경을 마련한다. 비밀번호·인증코드·토큰을 채팅으로 요청하지 않는다.

현재 운영에는 전용 스키마가 배포되지 않았으므로, 초안 규칙 자체의 실제 동작을 검증하려면 동일한 전체 규칙을 적용한 격리 테스트 DB/스테이징도 필요하다. 운영 규칙을 바꾸지 않은 상태에서 새 검증 항목이 운영에서 적용됐다고 판단하지 않는다. 실제 기존 사용자 데이터에 테스트 쓰기·삭제를 하지 않는다.
