# 사찰 수채화 대표 이미지 — 시범 3곳

실제 사진을 확인한 뒤 각 사찰의 영구 건축물·숲·시점을 바탕으로 개별 수채화를 생성했습니다. 사진에 없는 전각이나 산봉우리를 추정해 추가하지 않았습니다. 현장 실측 복원도나 실사 사진으로 표시하지 않습니다. 원본 사진이 보이지 않는 특성(예: 개암사 해당 시점의 바위산)을 상상해 끼워 넣지 않았습니다.

| 기존 카탈로그 ID | 이름/지역 | 개별 파일 | 참고한 모습 |
|---|---|---|---|
| temple:해인사 | 해인사 / 경상 | images/temple-covers/haeinsa-hapcheon.webp | 대적광전과 앞마당, 주변 전각·석탑·숲 능선 |
| temple:관음사 | 관음사 / 제주 | images/temple-covers/gwaneumsa-jeju.webp | 숲길의 석상·연등과 실제 먼 쪽 전각 |
| temple:개암사 | 개암사 / 전라 | images/temple-covers/gaeamsa-buan.webp | 대웅전의 지붕·문·돌축대와 숲 언덕 |

`manifest.json`에 사찰 ID·정확한 지역·파일·크기·SHA-256·사진 원본/작가/라이선스·가공 내역을 기록했습니다. 참고 사진은 Commons의 해당 사찰 카테고리·설명을 확인했습니다. 관음사는 **제주시 관음사**이며 다른 지역의 같은 이름과 연결하지 않습니다. 참고 사진의 썸네일 호스트는 403이라 재시도 후 정식 원본 URL로 내려받아 확인했습니다. 원본/생성본을 시각 비교했고 세 파일의 해시·경로가 다름을 검사합니다.

표시 시 기존 카탈로그 ID `temple:이름`과 `region`을 함께 검증합니다. 개인 Firebase 기록의 임의 키를 이 ID로 바꾸거나 새 ID를 저장하지 않습니다. 이름 일부가 비슷한 절, 다른 지역, 산에는 매칭하지 않습니다. 기존 `MASTER_BY_NAME`에서 각 ID가 정확히 한 사찰에 연결되는지 검사합니다.

대표 파일은 768×512 WebP이며 각 약 118~155KiB입니다. 목록에서 `loading=lazy`, 고정 종횡비를 사용합니다. 목록 검색/사진 교체 경로는 등록된 수채화를 건너뛰며, 실패해도 다른 절 사진으로 교체하지 않습니다. 상세 화면의 `firstPhotoUrl`, `fetchCoverPhotoNow`와 실제 사진·출처 표시·사용자 사진 저장/앨범 코드는 유지합니다. 카드의 ‘수채화·출처’ 링크에서 크레딧을 확인할 수 있습니다.

`tests/temple-covers.cjs`는 320/390/412/768/820/1440px에서 세 파일 실제 디코딩, 이름/지역/ID 일치, 지연 로딩, 외부 결과의 교체 차단, 상세용 사용자 사진/방문 기록 동일성, 이미지 실패 시 잘못된 사진 미노출을 검사합니다. 실제 iPhone Safari 검사는 완료하지 않았으며 운영 사이트에서 직접 확인할 수 있습니다.

이번에는 세 곳만 적용합니다. 다른 절은 현재 방식 그대로입니다. 확대 시 실제 참고 사진/사찰 동일성/라이선스를 확인한 뒤 WebP와 명시적 ID/지역 매핑을 추가하고, 중복 경로·해시 및 상세 사진 보존 검사를 다시 실행해야 합니다. 포괄적인 이름 검색이나 임의의 다른 사찰 이미지를 사용하지 않습니다.
