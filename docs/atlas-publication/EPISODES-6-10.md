## 변경 범위

- `index.html`: 큰 대표 배너·설명·별도 찾기 버튼 제거, 작은 회차 슬라이드를 ‘나의 108 순례’ 바로 위로 이동. 108순례 내부 HTML은 그대로 보존.
- `styles/atlas-home.css`: 작은 제목·카드·여백, 모바일 약 1.3개/태블릿 3개/PC 4개 표시.
- `scripts/atlas/home-carousel.js`: 소수점 너비를 포함한 실제 화면 좌표의 카드 간격에 맞춘 이동, 끝 지점 보정, 카드 전체 링크. 스와이프·화살표·키보드·페이지 표시 유지, 자동 재생 없음.
- `scripts/atlas/episodes.json`: 기존 5개 객체 유지, 새 회차 5개 메타데이터만 추가. 전체 목록 2,580바이트. 본문·문제·카드 데이터는 홈에 들어가지 않음.
- `sw.js`: 홈 CSS·JS 갱신을 위한 캐시 버전 변경. 서비스워커의 수송·오프라인 정책은 변경하지 않음.
- 새 5개 디렉터리: 각 `index.html`, `content.js`, `CREDITS.html`, `images/*.webp`, `images/manifest.json`.
- 회귀 검사: 기존 전체회차 검사를 목록 기반으로 확장하고, 새 회차별 읽기·문제·카드·저장 격리 검사를 추가.

## 역사 검토와 그림

원문 링크와 확인 범위는 각 회차 ‘역사 자료 보기’에 기록했습니다. 국가유산포털과 한국민족문화대백과사전 원문을 대조했으며, 자료에 차이가 있는 연대·해석은 확정하지 않습니다.

- 화엄사: 사자 네 마리·중앙 인물·맞은편 석등의 관계를 구분. 인물의 신원과 연기조사·어머니 이야기는 전승. 544년 창건설은 확정하지 않음. 각황전 앞 큰 석등과 효대의 인물 석등을 구별.
- 부석사: 선묘·용·뜬바위는 전설. 실제 바위는 지면 위의 형태로 표현. 무량수전은 신라 창건 때 건물이 그대로 남은 것으로 설명하지 않음. 서쪽 불단·동향 소조불상 배치 구분.
- 봉정사: 1625년 상량문에 전하는 1363년은 지붕 중수 기록. 최초 건립 연도가 아님. 극락전의 맞배·주심포와 대웅전의 팔작·다포를 구분.
- 법주사: 팔상은 여덟 생애 장면, 층수는 다섯. 현재 목탑은 전란 뒤 조선시대 재건. 석련지는 통일신라 석조 연못. 건축 모형과 재건·점검 장면은 설명용 창작.
- 대흥사: 금란가사·옥발우 세 개 등의 실제 목록 반영. 제목의 보따리는 비유이며 임종의 부탁을 창작하지 않음. 1602년 교지와 1794년 추모 글 구분. 해남 경내 표충사를 밀양과 구별. 13종사·13강사를 모두 휴정의 직접 제자로 설명하지 않음. 초의는 휴정보다 뒤의 인물.

표지 5점·장면 60점·카드 15점, 총 80점의 새 AI 수채화 창작 그림을 사용합니다. 실제 유물·건물의 실측 복원도나 기록 사진은 아닙니다. 인물·도구·작업 장면은 이해를 돕는 상상이며 실제 보존 공정 지침이 아닙니다. 원본 PNG는 웹 배포에 넣지 않고, 큰/작은 WebP 160개와 크기·SHA-256 목록만 배포합니다. 탑의 전체 형태가 잘리지 않도록 일부 그림은 크림색 여백 안에 전체 구도를 보존합니다.

참고 사진의 저작자·원문·라이선스·참고 범위와 그림의 창작/해석 범위는 각 `CREDITS.html`에 기록했습니다. 외부 사진 핫링크는 없습니다. 표충사는 문헌의 세 칸·맞배지붕 설명을 따랐고, 차 장면은 일지암의 현존 건물이나 초의 당시 건물의 복원도로 제시하지 않습니다.

## 데이터 보존

기존 1~5화 본문·이미지·저장 ID, 공통 렌더러·저장소·초기화·스타일, Firebase 설정·규칙·공개 정책은 변경하지 않았습니다. 운영 Firebase 데이터를 읽어 수정하거나 초기화하지 않았습니다. 기존 사진, GPS 인증, 순례·108 기록의 마이그레이션이나 삭제도 없습니다. 테스트는 격리된 로컬/모의 계정 데이터로 수행합니다.

## 검증 환경과 한계

Chromium의 PC 및 갤럭시 크기·터치 환경, WebKit의 아이폰·아이패드 크기·터치 환경에서 검사합니다. 실제 아이폰 Safari·갤럭시 Chrome·아이패드 실기기를 테스트한 것은 아닙니다. 실기기 GPS·통신사망·운영 사용자 계정의 쓰기 동작은 검사하지 않습니다.

최종 검사 결과와 성능 원자료는 같은 폴더의 `episodes-6-10-validation.txt`, `episodes-6-10-performance.json`을 참고하세요. 로컬 CPU 제한 측정은 실제 모바일망 Core Web Vitals나 구글 검색→사이트 진입 시간의 측정이 아닙니다.

성능 비교(390×844, Chromium CPU 4배 제한, SDK 지연 모의 응답, 외부 폰트 차단): FCP 중앙값 484→492ms, DOMContentLoaded 795→763ms입니다. 작은 차이이므로 실기기 개선의 증거로 보지 않습니다. 확실하게 확인한 변화는 섹션 높이 874→294px, 첫 썸네일 2→2개 유지, 홈의 새 6~10화 파일 요청 0건입니다. 이 조건에서 전체 홈 전송량은 21,226,540→21,224,237바이트이며 비밀도감만의 용량 수치가 아닙니다.
