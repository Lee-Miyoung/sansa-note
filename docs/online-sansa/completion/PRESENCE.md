# 실제 공동 참여 집계 · 운영 미활성

**현재 운영 숫자 집계는 비활성입니다.** `scripts/hall-presence.js`의 `PRODUCTION_READY=false`가 클라이언트의 새 서버 경로 읽기/쓰기를 모두 막습니다. 서버의 임의 값 하나만으로 활성화되지 않습니다. 기본 문구는 ‘참여 인원 확인 중’입니다. 정시 예불의 기존 공동 시계는 이 집계와 독립적으로 작동합니다.

## 구현한 연결 구조

- `scripts/hall-presence.js`: `.info/connected`, Google UID별 최대 3개의 비공개 접속 슬롯, 임시 UUID, 서버 타임스탬프, 45초 heartbeat, 재접속/퇴장/계정·법당 변경/화면 숨김/10분 조작 없음 정리.
- `functions/presence/`: Firebase Admin SDK·Functions v2 별도 Node 22 모듈, 의존성 잠금 파일 포함. 실제 기존 DB 위치와 같은 `asia-southeast1` 리전입니다. 실행/운영 배포는 하지 않았습니다.
- `onlineSansaPresence/sessions/{hall}/{uid}/{a|b|c}`: 자신의 Google 접속만 읽고 쓰는 제안 규칙. 실명·이메일·발원문·고민·GPS를 저장하지 않습니다.
- 먼저 `reserved`로 슬롯을 원자적으로 확보합니다. 예약은 집계하지 않습니다. `onDisconnect`를 `offline` 상태로 등록한 뒤 `online`으로 알립니다. 슬롯이 재사용되었을 때 옛 연결의 disconnect가 새 연결을 지우지 않도록 session ID가 같아야 offline 쓰기를 허용합니다.
- 정상 퇴장은 자신의 ID인 슬롯만 제거합니다. 숨김/10분간 조작 없음은 집계에서 빠지고, 돌아오거나 다시 조작하면 재가입합니다. 서버는 마지막 확인 120초가 지난 접속을 제외하며 분 단위 청소가 남은 항목을 지웁니다.
- 공개 경로는 `onlineSansaPresence/aggregates/{hall}/public`의 고유 계정 수·접속 세션 수·갱신 시각·집계 범위뿐입니다. 다른 사람의 UID/세션 목록을 브라우저에 내려보내지 않습니다.
- `count`는 Google **고유 계정 수**, `sessions`는 탭/브라우저 **접속 세션 수**입니다. 같은 사람이 모바일/PC/여러 탭을 열어도 고유 계정은 한 번만 셉니다. 물리 기기 수를 알아냈다고 주장하지 않습니다. 계정당 최대 3세션이라는 범위를 접근성 설명에도 표시합니다.
- 서버 집계가 실제 0인 경우만 0을 표시합니다. 없거나 오래되거나 권한 오류가 나면 숫자를 표시하지 않습니다. 공개 갱신 시각이 90초 이상 오래되면 숨깁니다.
- 집계 기준은 서버 소유 config의 `metric: "users" | "sessions"`로 정합니다. 기본은 고유 계정입니다. 클라이언트와 일반 관리자 UI가 config·집계 숫자를 쓸 수 있게 열지 않았습니다.

## 비용을 줄인 구조와 미검증 부분

heartbeat의 타임스탬프마다 모든 시청자에게 다시 전파하지 않습니다. 서버 이벤트는 `phase` 변경에 연결하고 예약/정리 중 실제 온라인 변화가 아닌 이벤트는 집계 읽기를 하지 않습니다. 누락/TTL 처리를 위한 주기 재집계는 분당 1회, 여섯 법당이며 함수 최대 인스턴스는 변경 처리 2개·정기 청소 1개입니다.

수학적 예시: 하루 100개의 접속 세션이 각각 1시간 사용하면 heartbeat는 약 8,000회(45초 간격), 입장/퇴장 상태 쓰기 등을 보수적으로 합쳐 약 8,400회입니다. 정기 서버 함수 호출은 하루 1,440회, 여섯 법당의 정기 읽기는 약 8,640회이며 입퇴장에 따른 추가 읽기가 있습니다. 실제 RTDB 전송량/청구액은 접속 분포·재시도·SDK 프로토콜·요금제에 따라 달라집니다. 이 계산을 운영 과금 검사 완료로 주장하지 않습니다.

**실제 기존 상위 규칙·App Check/남용 방지·호출/비용 예산·부하 검증은 완료하지 않았습니다.** 최대 인스턴스는 청구액의 하드 상한이 아닙니다. 이 검증이 끝날 때까지 rollout을 활성화하지 않습니다.

## 준비된 검증

- `node tests/presence/client.cjs`: 예약→disconnect 등록→온라인 순서, 끊김/복귀/비활성, 오래된 값, 실제 0, 게스트 읽기 전용, 빠른 계정/법당 변경과 지연된 옛 삭제의 경쟁, 중복 계정/여러 세션, TTL, 공개 값의 UID 부재. 통과했습니다.
- `node tests/presence/ui.cjs`: 테스트에서만 rollout을 켜고 **모의 서버 스냅샷** 2→1과 오래된 값 숨김을 검사했습니다. 캡처에도 ‘모의 서버 집계 검증 · 운영 참여자 수가 아닙니다’ 표시가 있습니다.
- `tests/presence/rules.cjs`: demo 전용 에뮬레이터 검사로 Google 소유권·게스트 거부·위조 집계/UID/이메일/GPS 거부·3슬롯·업데이트 빈도·ID 불일치 offline 거부·중단 후 정리·기존 데이터 보존을 검사하도록 준비했습니다. **JAR 다운로드 차단으로 아직 실행하지 못했습니다.**

## 운영에 켜기 전 필요한 실제 단계

1. 권한 있는 관리 환경에서 현재 운영 규칙을 읽고 보관합니다. 상위 경로에 광범위한 read/write 허용이 있으면 하위 false로 제한할 수 없으므로 반드시 검토합니다.
2. [새 경로만의 추가안](presence-rules-additions.json)을 실제 규칙에 안전하게 병합합니다. 테스트 fixture 전체를 운영 규칙으로 사용하지 않습니다.
3. demo 에뮬레이터에서 `tests/presence/rules.cjs`와 기존 데이터 경로 검사를 통과시킵니다. 추가안이 운영 전체 규칙과 같은 것이라고 간주하지 않습니다.
4. 운영 비용/남용 방지·리전/인스턴스·서비스 계정 최소 권한을 검증한 뒤 별도 Functions를 배포합니다. 기존 사용자 기록을 테스트 목적으로 고치지 않습니다.
5. 테스트 계정/기기 2개로 실제 join/disconnect/재연결·중복 계정·시간 초과·공개 UID 비노출·거부 동작을 검증합니다.
6. 서버 config를 예컨대 `{enabled:true,metric:"users"}`로 준비하고 정기 집계의 공개 값이 확인된 후, 코드의 `PRODUCTION_READY`를 새 검증 커밋으로 켭니다. 실제 서버 검증 결과와 SHA를 남깁니다.

이번 환경에는 관리자 자격 증명이 없으며 규칙/함수 배포를 수행하지 않았습니다. 사용자에게 확인되지 않은 동시 참여 수를 보여주지 않기 위한 미활성 상태입니다.
